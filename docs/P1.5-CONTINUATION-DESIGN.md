# P1.5: continuation inventory and design checks

This follow-up to [P1](P1-SERIALIZABLE-CONTINUATION.md) inventories the generated
game corpus and exercises additional isolated continuation cases. It does not
integrate savestates into the application.

Validation on 2026-09-23 passed: five audit tests, six schema tests, exact audit
reproduction, P1 fresh-process restore for both FR modes, generated-flow checks
in normal and ASan/UBSan builds, and O0 PIE ↔ O2 non-PIE snapshot exchange in
both directions. Leak checking was disabled for the sandbox's ptrace constraint.

## Corpus evidence

The reproducible [audit](P1.5-CORPUS-AUDIT.json) contains 1,981 generated functions
in 40 C files (16,131,668 source bytes). Function call profiles partition into
1,679 direct-only, 27 indirect-only, 33 mixed and 242 without emitted C calls.
There are 87 emitted indirect regular calls and one indirect tail call.
The inventory also finds 84 switches in 82 functions, 873 candidate backward
edges and 160 branch-likely instruction sites.

All functions declare `hi`, `lo`, `result` and `c1cs`; 84 additional declarations
are jump-table scratch locals. These are syntactic counts, not liveness results.
The current P1 backend rejects indirect transfers and jump tables, so its passing
tests do not establish whole-corpus coverage.

Reproduce the checked-in report, including optional ELF symbol evidence:

```sh
python3 -m unittest discover -s tests/continuation_audit -v
python3 scripts/audit_continuations.py --summary \
  --elf ../snowboardkids-decomp/build/snowboardkids.elf \
  --output /tmp/continuation-audit.json
cmp docs/P1.5-CORPUS-AUDIT.json /tmp/continuation-audit.json
```

See the [audit notes](../tests/continuation_audit/README.md) for counting rules.
The JSON's source growth figures are adjustable assumptions, not measured output
sizes. Its declared 266 sections are not 266 active overlays.

## Identity and execution probes

The [design checks](../tests/continuation_design/README.md) provide runnable
commands and precise coverage. The proposed schema derives function identity
from image digest, section ROM range, guest offset and role. Continuation labels
include instruction offset, owning transfer, phase and emission variant. Typed
scalar fields form a canonical manifest independent of discovery order. This is
a separate specification model; P1 still uses its original fixed-section IDs.

The generated-flow probe exercises three calls through one loop, both outcomes
of ordinary and likely branches, and preservation of live HI/LO/c1cs across
calls. Its initial decoder failure was resolved by matching the pinned CLI's
pseudo-instruction settings. No dependency sources were modified.

The cross-build probe checks fresh-process restoration between differently
optimized binaries with different host address-layout policies. It requires
identical semantic generated code and does not promise save compatibility across
game, generator or schema changes.

## Performance scope

An initial local no-park microbenchmark measured a native median of 66.75 ns and
an explicit-frame median of 111.32 ns per fixture execution (1.67x). Host frames
were 48 bytes. These measurements include reset and queue operations and exclude
serialization, actual blocking and worker scheduling. Host load and compiler
choice affect the result; rerun the benchmark for comparisons. No gameplay
performance conclusion follows from this tiny call chain.

## Next implementation boundary

Before whole-game conversion, the backend needs typed source-PC and delay-slot
metadata, indirect/tail/overlay transfer handling, jump-table local preservation,
and validation of every supported call edge and schema. Scheduler/HLE ownership
and capture barriers remain separate requirements in the
[native savestate design](NATIVE-SAVESTATES-DESIGN.md). The current work supports
proceeding with those isolated backend experiments, not exposing save/load UI.
